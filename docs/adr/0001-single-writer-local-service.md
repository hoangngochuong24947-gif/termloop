# 词表由本地单写端服务持有，而非浏览器数据库

## Status

accepted

## 背景

v1.0 的 PRD 把真相源放在浏览器 IndexedDB（Dexie），理由是零运维、离线可用、单机够用。这个选择在「单人自用」的前提下成立，但和两条新需求直接冲突：

1. 词表要能被本地 Agent 读写。浏览器数据库没有端口、没有文件、没有协议，任何外部进程都够不到它——「把接口暴露给 Agent」在 Dexie 方案下物理上不可实现。
2. 手机要能用。IndexedDB 是按浏览器 profile 隔离的，Mac 和 iPhone 各有一个库，数据不流动。

## 决定

数据真相源是一个 **SQLite 文件 + 一个常驻本地进程**，该进程是数据库的**唯一写入者**。

- 端口默认 `127.0.0.1:7788`，同时提供 JSON API 与已构建的前端静态资源。
- 所有写入（UI、CLI、MCP、外部 Agent）一律经 HTTP 或 CLI，**任何客户端都不直接打开 SQLite 文件**。
- 读用 WAL，允许多个只读连接并发。
- 词表额外以行式 JSONL 快照落到 `termbank/`，进 git——数据库负责运行态，文本负责可 diff 的资产形态。

## 考虑过的方案

| 方案 | 为什么没选 |
|---|---|
| 保持 Dexie | 外部 Agent 无法写入；多设备数据割裂。见上方背景。 |
| 文件即真相源（词表是 git 里的 YAML，服务只做索引） | 对 Agent 最友好，但复习记录是高频遥测（每天上百条），塞进 git 文件会又脏又慢；且「UI 改一条」与「Agent 改一条」会形成两个写入端。 |
| SQLite + 文件双向同步 | 双真相源必然漂移，需要冲突合并，复杂度远超单人自用的收益。 |

## 后果

- 需要处理「本机 HTTP 服务」的安全问题：任意网页都能 `fetch` 到 localhost，因此 API 强制要求 Bearer token，并校验 `Origin`。见 PRD §6.6。
- 手机端不再是独立副本，而是同一个实例的瘦客户端（经 Tailscale 或局域网），离线时只读缓存。
- 部署形态从「静态托管」变成「跑一个进程」，备份从「手动导 JSON」变成「复制 SQLite 文件 + git 里的词表快照」。
